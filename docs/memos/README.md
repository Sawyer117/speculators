## `adaptive-spec-graph-mode-ascend.pptx`

**自适应投机解码的图模式代价 —— 昇腾 NPU 上的真实瓶颈在哪(通用模型与 DSV4 两条路线)。**
7 页,全中文。重新生成:`python3 make_adaptive_spec_memo.py --out <file>.pptx`(需 `python-pptx`)。

自适应投机按置信度给每个请求分配 K_i,只验证值得验证的 token;设备图则要求形状、地址、执行路径固定。
备忘录回答的不是"能不能省 token"(一定能),而是**为适配图付出的额外开销是否吃掉收益**。

三条结论,均有代码/文档出处:

1. **GPU 参考被高估。** vLLM PR #48692 已关闭未合入,**明确不做在线预算分配**(改用用户配置的
   `num_speculative_tokens_per_batch_size`),仅支持 `FLASH_ATTENTION`,作者自述**测不出加速** ——
   唯一被证实的收益是固定预算下的接受率(3.707,对比静态 K=5 的 3.445 / K=7 的 3.918)。
   它是"变长如何与全图共存"的参考,不是加速证据。

2. **设备侧长度已经存在,但只在一族算子上。** FIA v2(`npu_fused_infer_attention_score_v2`)的
   `actual_seq_qlen` 是 Host 侧 int 数组,vllm-ascend 全部调用点都用 `.tolist()` 构造;而
   DSA / lightning-indexer / SFA(`torch.ops._C_ascend.npu_vllm_*`)的签名就是 `torch.Tensor`,
   调用处传 `query_start_loc[1:].clone()`,全程不过 host。**DSV4-Flash 走 DSA 路径,前置条件已满足;
   通用稠密模型走 FIA 路径,这才是卡住的地方。**

3. **增量代价被误判。** 固定-K 投机早已入图,replay 前逐层更新 seq lengths 的 `graph_task_update`
   开销**已经在付**;动态 K 的真正增量是 **workspace 每轮 miss**(缓存键正是"本轮总 token 数")、
   **图键爆炸**与 **padding**。修法是结构性的:缓存键与图键都改为
   `(batch bucket × 总验证 token bucket)`,捕图阶段一次性预分配。

**推进顺序**:先在 DSV4/DSA 上把动态 K 端到端跑通并量化收益(前置条件最全、最快回答"值不值得"),
结论为正再推动 FIA v2 的接口改动,让通用模型受益。

### 与 v2 的实质差异

1. **立项理由改为可量化的主因。** #48692 实测:同等验证预算下(上限 K=7、每请求有效 K=5)接受长度

2. **新增一页"上游已经做到哪一步"**,列出 #47808 的四条机制(生存概率打分的 Triton kernel、

   与三条限制(不支持 LoRA / 流水并行 / 输出 logprobs)。
3. **新增一页"昇腾侧的三个真实缺口"**,均经源码核实:confidence head 在 vllm-ascend 未被加载

   那个 PR);无支持变长 decode 图的昇腾后端(★ 主要风险与主要投入);预算调度 kernel 无昇腾实现。
4. **阶段 0 由"两周量化"缩为"一天判定"** —— 收益幅度上游已用数据回答,我们只需把自己的加速比

## `preview_pptx.py` — 版式自检工具

沙箱内没有 LibreOffice,做不到所见即所得。这个脚本从 pptx 读出形状几何与文字,用 PIL 近似重绘成 PNG,
**专门用来查版式重叠与文字溢出**(文本超出所在形状时会被红框标出)。

它不是保真渲染器 —— autoshape 箭头会被画成方块,换行也只是近似;它的用途是发现错误,不是预览成品。

```bash
python3 preview_pptx.py <deck>.pptx <out_prefix> [页码 ...]
```

需要一个 CJK 字体,路径写在脚本顶部的 `FONT` 常量里(字体本身未入库)。
v3 的一页纸靠它发现并修掉了三处文字溢出;后来又加了 `overlaps()`,查出两处**形状互相压盖**
(其中「四、实施方案」那处从 v3 初版就存在,表格底部压住了下面的文字块)。这两类错误坐标算术都发现不了。

### v3 的两页技术补充

面向**没有上下文的听众**,先讲机制再落算子,分成两页:

**「三(补充 1)、为什么「变长」会掉出设备图」** —— 设备图(昇腾 ACL Graph / GPU 侧 CUDA Graph)是把一串算子
按**固定的张量形状与地址**预先录制、之后整段重放,省掉逐算子下发开销;解码是「算子小、次数多」的场景,
这部分开销占比很高,所以能否入图直接决定性能 —— **而录制的前提就是每一步形状都一样**。
页面用一张对照图说明:固定 K=5 时四个请求各 5 个 token、总数恒为 20,形状固定可入图;自适应下
K_i = 5/2/7/1、总数 15 且下一步又变,query 长度参差(ragged)→ 默认掉出图。
⟹ 问题于是归结为一件具体的事:**图里依赖序列长度的参数,是录制时固化的常量,还是运行时可改内容的设备张量?**

**「三(补充 2)、落到算子:逐个部件核对」** —— 回答上面那个问题,四行结论全部标注 vllm-ascend 的文件与行号:

| 部件 | 现状 | 对变长 K 的意义 |
|---|---|---|
| 通用 FIA v2 | 序列长度是 host 侧 `list[int]`(`attention_v1.py:183`,由 `query_start_loc_cpu[1:].tolist()` 构造,`:314`) | 值在捕获时被烘进图,K 一变必须重捕 —— 这是「任意形状不可入图」的机械原因 |
| ★ DSV4 的 DSA/SFA | 序列长度是 device tensor(`device_op.py:559`;`dsa_v1.py:1061` 传 `query_start_loc[1:].clone()`) | 图捕获的是指针不是值,结构上**不需要重捕** —— 我们主攻的路径在更有利的一侧 |
| workspace | 按 token 数做缓存键(`attention_v1.py:490/636/812/953`;`num_tokens = actual_seq_lengths_q[-1]`,`:774`) | K 变 → 缓存未命中重新分配;K 组合一多,图与 workspace 数量一起膨胀 —— ★ 真正的成本 |
| 图内元数据更新 | 机制已存在(`attention_v1.py:530-565` 的 `graph_task_update_begin/end` 块内已有 `_EXTRA_CTX.is_draft_model`) | 固定 K 投机**已经在图里跑**,逐 draft step 更新的开销已经付过 |

⟹ 因此准确的风险表述**不是**「昇腾不能变长入图」,而是:两项结构性条件已具备,
未知量集中在 **workspace 与图数量随 K 组合的膨胀**及其显存 / 捕获耗时。
这决定了阶段 2 的第一件事是**先量形状数量与 workspace 膨胀**,再选路线,而不是先写实现。
